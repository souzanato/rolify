= Upgrade instructions for Rolify library

== From rolify 6.x to 7.x

=== Requirements

Rolify 7 requires Ruby 3.2 or newer, and ActiveRecord 7.1 or newer (or
Mongoid 9). No public API changed, so an application that already runs on those
versions needs no code change.

=== Adding the unique indexes (ActiveRecord)

A role is identified by its name at one of three levels, and the migration
generator now creates one partial unique index per level:

    global     UNIQUE(name)                          WHERE resource_type IS NULL     AND resource_id IS NULL
    class      UNIQUE(name, resource_type)           WHERE resource_type IS NOT NULL AND resource_id IS NULL
    instance   UNIQUE(name, resource_type, resource_id)                              WHERE resource_id IS NOT NULL

plus <tt>UNIQUE(user_id, role_id)</tt> on the join table. The old single index
over all three columns did not cover the global and class scoped levels,
because a database treats NULLs as distinct in a unique index, so two
concurrent creations of the same global or class scoped role could both
succeed.

+You do not have to add these indexes.+ They only make the database enforce
what Rolify already does. But an existing installation may well contain
duplicates that the old index allowed, and those have to be dealt with before
the indexes can be created. Rolify cannot decide for you which row to keep, so
no migration is provided.

==== 1. Find the duplicates

    # global
    Role.where(:resource_type => nil, :resource_id => nil)
        .group(:name).having("COUNT(*) > 1").count

    # class scoped
    Role.where(:resource_id => nil).where.not(:resource_type => nil)
        .group(:name, :resource_type).having("COUNT(*) > 1").count

    # instance scoped: the old index already prevented these, but check anyway
    Role.where.not(:resource_id => nil)
        .group(:name, :resource_type, :resource_id).having("COUNT(*) > 1").count

==== 2. Merge them

Which row survives, and whether a user should end up holding the merged role,
is a business decision. What matters technically:

* role assignments live in the join table, so a merged role has to keep the
  assignments of the rows it replaces;
* the join table has a unique <tt>(user_id, role_id)</tt>, so if a user holds two
  of the duplicate roles, one of those two assignment rows has to go before the
  second can point at the surviving role.

Do that in a data migration you write and review, not in the schema migration
below.

==== 3. Create the indexes

Only PostgreSQL and SQLite support partial indexes. On any other adapter the
generator falls back to the old single composite unique index, which only
covers instance scoped roles; skip to the note at the end.

    class AddRoleScopeUniqueness < ActiveRecord::Migration[8.1]
      # Replace :roles / :users_roles if you renamed the role class or the join
      # table, and remove the old index first (it has the same columns as the
      # instance scoped one below).
      def change
        remove_index :roles, [ :name, :resource_type, :resource_id ]
        add_index :roles, :name

        add_index :roles, [ :name ],
                  :unique => true,
                  :where => "resource_type IS NULL AND resource_id IS NULL",
                  :name => "index_roles_global"

        add_index :roles, [ :name, :resource_type ],
                  :unique => true,
                  :where => "resource_type IS NOT NULL AND resource_id IS NULL",
                  :name => "index_roles_class_scoped"

        add_index :roles, [ :name, :resource_type, :resource_id ],
                  :unique => true,
                  :where => "resource_id IS NOT NULL",
                  :name => "index_roles_instance_scoped"

        remove_index :users_roles, [ :user_id, :role_id ]
        add_index :users_roles, [ :user_id, :role_id ], :unique => true
      end
    end

Add the indexes under new names rather than reusing
<tt>index_roles_on_name_and_resource_type_and_resource_id</tt>, so the old index
can be dropped independently.

==== MySQL and MariaDB

These adapters have no partial indexes, so the three levels cannot be enforced
separately in the database. The generated migration uses
<tt>UNIQUE(name, resource_type, resource_id)</tt>, which covers instance scoped
roles only. Global and class scoped roles continue to rely on Rolify's
<tt>find_or_create_by</tt>, so concurrent creation of one of those can leave
duplicates. Add <tt>validates :name, :uniqueness => { :scope => [...] }</tt> to
your Role model if you need a stronger guarantee, accepting that a validation is
still subject to a race.

== From a previous rolify installation (1.x or 2.x)

The easiest way is to re-run the generator using <tt>rails g Rolify:Role</tt> command, and overwrite the initializer file. Both the migration file and the <tt>role.rb</tt> haven't changed.
In the <tt>config/initializers/rolify.rb</tt> file, here are the deprecated settings:
* <tt>role_cname</tt>
* <tt>user_cname</tt>
By default, these settings were commented out, so you can safely remove them. 
If you changed them, you can remove them in the initializer file too. <tt>user_cname</tt> is no longer used in 3.x, you don't need it anymore.
Add your custom <tt>role_cname</tt> setting as argument of the rolify method you use in your User class. 
For instance, if you use <tt>Privilege</tt> as <tt>Role</tt> class, you should add this to your whatever your <tt>User</tt> class is, let's say <tt>Client</tt> for the sake of example: 
   class Client < ActiveRecord::Base
     rolify :role_cname => "Privilege"
   end
If you use the default <tt>Role</tt> class name, you don't have to specify the <tt>:role_cname</tt> argument.

If you use <i>dynamic methods</i> (<tt>user.is_admin?</tt> like methods), you should turn it on using <tt>use_dynamic_shortcuts</tt> method starting from rolify 3.0:
   Rolify.configure do |c|
      c.use_dynamic_shortcuts
   end
The old fashion way still works though, but won't work anymore if the setter method name is changed in a possible future. You've been warned :-)

== From a rolify installation 3.x

=== Dependencies: 

Starting from 3.3 release, rolify supports Rails 3.2 and newer.

Mongoid callbacks are supported if Mongoid 3.1 and newer is installed.

=== Rails Generators

Role model template when using Mongoid has been changed, you should re-run the generator.

Rails generator has been renamed to: <tt>rails g rolify</tt> and arguments have been changed: 
* Role class name is now mandatory, User class name remains optional and its default is still <tt>User</tt>
* ORM optional argument is now <tt>-o</tt> or <tt>--orm=</tt>
For instance, here is a new rolify generator command example: <tt>rails g rolify Role</tt>
You can use <tt>rails g rolify --help</tt> to see all available options.

=== Testing

Starting from rolify 3.3, to run the specs you should run: <tt>rake spec</tt> or simply <tt>rake</tt>.
